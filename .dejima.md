# Working on meeseeks

Notes for an agent working **on this repo**. What meeseeks does for its users is in `README.md`.

## Security here is not a later pass

meeseeks stands between a chat room and agents running in dejima sandboxes, and it holds the line dejima draws: the agent is presumed hostile. A change that quietly weakens one of the boundaries below is a defect in the product, not a rough edge to tidy up later. If you notice one while doing something else, say so rather than leaving it for a pass that may not come.

The boundaries, and what keeps each:

- **`~/shared` is the session's to change, concurrently.** The host reads and writes it by descriptor, never by path: `O_PATH` and `fstat` before reopening anything (`archive.build`, `archive.read_file`), `O_NOFOLLOW` on every component, `O_EXCL` on every file created (`launch.upload`). Nothing from it is trusted but the bytes of a file checked to be regular. A device node can't be opened just to look at it.
- **The forced command is the only way in to the dejima host.** `launch.command` accepts a fixed grammar, and the launcher re-validates every job and request it is handed, whatever the API checked.
- **What a requester approves is what is granted.** A domain request is granted from the launcher's saved copy, intersected with what the API's policy passes; neither the agent's file nor either side alone can widen it.
- **Agent-written text reaches chat inert.** Escaped HTML, links shown with their destination (`plugin/meeseeks_bot/markdown.py`), empty `m.mentions`, labelled untrusted. Text typed into a session has control characters stripped and a prefix, so it can't end the bracketed paste or start a harness command.
- **The bot acts only for allowlisted users**, and a reply counts as being about a session only when the replied-to message is the bot's own, carrying its tag.
- **The API scopes everything by client token**, and errors relayed to chat don't carry host paths.

A change touching any of these gets an adversarial review before its pull request, with the threat model stated, and the review's findings fixed or answered in the pull request.

## Tests

`.venv/bin/python -m pytest` runs everything, and all of it runs in a sandbox. The one thing a sandbox can't do is build the API's image, which needs Docker; CI does that on every pull request in its `privileged` job, so say in the pull request that the image wasn't built locally rather than stopping.

Read pytest's exit status and its summary line, not the absence of failures. A test file that fails to import is reported as an error, not a failure.

Some tests check permissions and skip as root, which ignores them. CI runs as an unprivileged user so they don't; if you run as root, say which skipped.

## A test that reads its environment passes in one place and fails in another

The launcher reads `PATH`, `XDG_RUNTIME_DIR`, the euid and the clock. A test that depends on any of them sets it (`monkeypatch.setenv`, a fake binary on `PATH`, `os.utime`) rather than inheriting it. When a test fails only in one environment, suspect this before suspecting the code.

## Pushing a branch here runs your code outside the sandbox

CI checks out each pushed commit and runs the tests on a host, outside this sandbox's firewall, with no one reading the diff first. Every file in `tests/` is code that runs there. Write test code you'd be comfortable running on that host.

What CI may reach is `.dejima/allowed-domains`, which the runners' egress allowlist reads from `main` and treats as already reviewed. Adding a domain widens what every future CI job here can talk to from the moment it merges, so say in the pull request what it's for. A new destination only works once that change is on `main`.

## Batch your pushes

Every push to an open pull request starts a full workflow run, and Gitea queues runs rather than superseding them. Commit as often as you like; push once a change is finished. If a push leaves a run you no longer need, cancel it in the web UI.

## Write the comment that prevents the bug, not the one that shows your work

- **Keep** the issue number, the failure mode, and why a check is shaped the way it is, as a property of the code that is there.
- **Cut** how you found it, what the code replaced, the second and third consequence, anything the code below already says, and meta-commentary.
- **No numbers that drift**: test counts, sizes, how many of anything. That includes pull request descriptions.

Length carrying a fact is fine. Length carrying none is not.

## Target `development`, not `main`

Branches are opened against `development`, which merges to `main` when it is ready to release. Rebase onto `origin/development`, and pass `--base development` to `gitea-pr create`. Report the base it printed, not the one you meant: a pull request URL looks the same whichever branch it targets.
